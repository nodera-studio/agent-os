# Building a Token-Efficient, Exa-Style Semantic Web Fetch Layer for Claude — Buy, Build, or Blend?

## TL;DR

- **Build the extraction/relevance layer locally, and treat a cloud “neural search” API as an optional discovery front-end, not the core.** The single biggest win — cutting per-fetch token cost by roughly 90–95% versus raw HTML — comes from local content-cleaning + query-relevant chunk selection, which you can build cheaply on top of Mnemosyne’s existing pgvector + RRF + MLX embedding stack. Per Exa’s engineering blog, on SimpleQA “500 characters of Exa’s highlights match the accuracy of the first 8000 characters of the page, and use 16x fewer tokens,” and “4k characters of highlights is better than 32k characters of full text” (~94% fewer tokens on some evals).
- **For the search-index half (finding URLs), you cannot fully replicate Exa locally** — its neural index over tens of billions of pages is the one piece that is genuinely hard to self-host; SearXNG (self-hosted metasearch) is the realistic free substitute, and Exa’s own MCP server (free tier: $20 signup + $10/month credits) is the lowest-effort paid option if you want neural recall.
- **Recommended architecture: SearXNG (self-hosted search) → Trafilatura (local extraction) → chunk → MLX-served local embeddings → pgvector top-K + local reranker → return only top chunks, all exposed as one custom MCP server that reuses Mnemosyne.** This keeps every query and fetched page on your M5 Max (important for Adobe-adjacent work), costs $0 per query, and gives you an incrementally-growing personal web cache.

## Key Findings

1. **Exa returns clean, query-relevant excerpts, not raw HTML, by combining a neural (embedding) index with an in-house “highlights” model.** Its `highlights` feature chunks and embeds each page with a paragraph-prediction model and returns only the most query-relevant sections, running fresh per request in under 100ms. Exa reports highlights give “higher quality results for ~94% fewer tokens on some evals,” and that 500 characters of highlights match the accuracy of the first 8,000 characters of a page (16× fewer tokens).
1. **Exa ships an official, free-to-install MCP server** (`exa-mcp-server`, plus a hosted remote at `https://mcp.exa.ai/mcp`) that plugs directly into Claude as a native connector. Using it directly is far simpler than building an equivalent for the *search* half.
1. **The “LLM-native search API” category is crowded and mostly cheap-ish per query but paid and cloud-hosted:** Exa ($7/1k searches), Tavily (~$5–8/1k, acquired by Nebius Feb 2026), Brave Search API ($5/1k, independent index), Perplexity Sonar ($1/1k + tokens, returns synthesized answers), Kagi ($12–25/1k), Jina Reader (~$0.02/1M tokens, URL→markdown). Most now offer official MCP servers.
1. **The content-cleaning half is a solved local problem.** Trafilatura is the accuracy leader among open-source extractors (F1 ~0.94–0.96), fast (~14–22ms/page, no GPU), and directly usable in Python. Jina Reader, Firecrawl, and Crawl4AI are heavier alternatives.
1. **Self-hosting the search layer with SearXNG is realistic on a Mac or a $5/month VPS**, runs in Docker, uses ~200MB RAM, and exposes a clean JSON API (`/search?q=...&format=json`) built for exactly this kind of programmatic/agent use.
1. **Reference implementations of the exact “fetch→extract→chunk→embed→return-top-K” MCP pattern exist but none combine all your specific choices** (local embeddings + pgvector + web fetch). The closest are `coleam00/mcp-crawl4ai-rag` (fetch+chunk+embed+pgvector+MCP, but cloud embeddings by default) and `shinpr/mcp-local-rag` / `nkapila6/mcp-local-rag` (local embeddings, but in-memory or SQLite/Chroma).
1. **Persisting fetched-and-embedded content into pgvector to build a re-queryable personal web cache is a well-established pattern** and a natural extension of Mnemosyne — no mature turnkey tool does exactly this, so it’s a genuine open niche you’re well-positioned to fill.

## Details

### 1. How Exa.ai actually works

Exa (formerly Metaphor, founded 2021 by Will Bryk and Jeff Wang) is a web search engine built for AI agents rather than humans. Its core differentiator is **neural/embeddings-based search**: instead of keyword matching or PageRank, Exa trained a link-prediction model that learns which documents follow a given piece of text, so a natural-language or paragraph-length query is embedded and matched against embeddings of a pre-built index of tens of billions of web pages. It supports three modes — neural, keyword, and hybrid — plus an `auto` mode that picks per query. (The old `useAutoprompt`/query-rewriting flag is now deprecated.)

Crucially for token cost, Exa **does not return raw HTML**. Its endpoints let you request, per result: `text` (cleaned full text, boilerplate/nav/ads stripped), `highlights` (the most query-relevant excerpts), and `summary` (an LLM-generated summary). The **highlights** feature is the key mechanism: a paragraph-prediction model chunks and embeds each page, then returns only the top semantically-relevant passages, scored against the query. Exa states highlights run fresh for every request (not cached), complete in under 100ms, and can “reduce token budgets and LLM costs by over 50% compared to passing entire pages.” Its engineering blog (“Exa Highlights,” exa.ai/blog/highlights-for-agents) reports stronger numbers on some evals: “higher quality results for ~94% fewer tokens on some evals,” and “On benchmarks like SimpleQA, 500 characters of Exa’s highlights match the accuracy of the first 8000 characters of the page, and use 16x fewer tokens… 4k characters of highlights is better than 32k characters of full text.” A third-party (“QueryBurst”) replication built a similar pipeline (fetch+clean via markdown → sentence split → hypothetical-answer embedding → rank) and reported 75% SimpleQA accuracy at ~397 tokens vs 65% at ~878 tokens for full-page  — confirming the approach is reproducible with open tooling, and that on *fresh* (un-indexed) pages Exa also computes embeddings on the fly in ~3 seconds, i.e. its speed edge is precomputed index coverage, not a fundamentally different architecture.

**Pricing (verified July 2026):** pay-as-you-go, no monthly minimum. Per Exa’s pricing changelog: Standard Search $7/1,000 requests (10 results, text + highlights included; raised from $5 in a March 2026 update), $1 per 1k additional results beyond the 10th. Deep Search $12/1k, Deep-Reasoning $15/1k, Answer $5/1k, Contents endpoint $1/1,000 pages per content type, AI summaries $1/1,000 pages, Monitors $15/1k. Since March 2026, page contents for the first 10 search results are bundled into the $7 search price. Free tier: $20 signup credits + $10/month with full API access; an unauthenticated MCP tier allows 3 QPS / 150 calls/day. **Funding note (corrected):** Exa raised an **$85M Series B in September 2025 led by Benchmark (Lightspeed participated) at a ~$700M valuation**, then a **$250M Series C led by a16z at a $2.2B valuation, announced May 19, 2026** — so this is a well-capitalized, fast-moving vendor, not a fragile one.

### 2. Exa’s official MCP server

Yes — Exa maintains `exa-mcp-server` (open source, on GitHub at exa-labs/exa-mcp-server) and a hosted remote server at `https://mcp.exa.ai/mcp`. It installs into Claude as a **native connector** (Claude Desktop → Settings → Connectors, no config file needed) or via `claude mcp add`. Tools exposed include `web_search_exa`, `web_fetch_exa`, `get_code_context_exa` (search GitHub/docs/Stack Overflow), `company_research`, `linkedin_search`, `crawling`, `deep_researcher_start`/`deep_researcher_check`, and an `agent_run` tool; a newer `web_search_advanced_exa` supersedes some older tools.  By default only `web_search_exa` and `get_code_context_exa` are enabled. It offers an **unauthenticated free MCP tier** (3 QPS / 150 calls/day) and a generous free plan; adding your own `EXA_API_KEY` (via `x-api-key` header or env var) removes rate limits and uses the same pay-as-you-go pricing above. **Verdict: for the search-discovery half, using Exa’s own MCP server directly is dramatically simpler than building an equivalent** — the hard part (the neural index) is what you’d be paying for.

### 3. Competing LLM-native search APIs

- **Tavily** — purpose-built for RAG/agents; returns clean structured results with pre-extracted snippets ready for context injection. ~$5–8/1,000 basic queries; 1,000 free/month. Official MCP server. Founded 2024 (Rotem Weiss, Assaf Elovic, Yuval Rozio) and reporting over 3M SDK downloads/month, it was **acquired by Nebius (NASDAQ: NBIS), announced Feb 10, 2026, for $275M cash (up to $400M on milestones)**, now being folded into Nebius’s web-gateway stack — a data-residency consideration.
- **Brave Search API** — independent index (not Google/Bing reselling), clean JSON, “Data for AI”/LLM-context tier delivers pre-chunked relevance-ranked Markdown. ~$5/1,000 (some tiers $3), 2,000 free/month. Fastest in one AIMultiple benchmark (669ms). Official MCP server. Best pick when index independence/privacy matters.
- **Perplexity Sonar** — returns a *synthesized, cited answer* rather than raw results; ~$1/1,000 requests plus token fees. Best when you want a finished paragraph; redundant if Claude itself is your synthesizer.
- **Kagi Search API** — premium re-ranked results; $12–25/1,000 (rebuilt “v1” Search + Extract APIs; FastGPT summarizer endpoint). Hosted MCP server available (Search + Extract). Higher per-query cost, high quality.
- **You.com API** — Web Search + Research tiers; leads some factuality benchmarks; ~$0–50/1k depending on tier.
- **Jina AI Reader** (`r.jina.ai` URL→markdown, `s.jina.ai` search) — the most directly relevant to your goal: prepend `r.jina.ai/` to any URL and get clean LLM-ready markdown, handling JS rendering server-side. ~$0.02 per 1M output tokens, 10M free tokens per key. Official remote MCP server (`jina-ai/MCP`). Jina was **acquired by Elastic (NYSE: ESTC), completed Oct 9, 2025** (founder Han Xiao became Elastic’s VP of AI). This is the cheapest cloud “clean-a-URL” option and a good fallback for pages your local extractor chokes on.
- Also in the category: Firecrawl (search+scrape+crawl, credit-based ~$83–99/mo, AGPL, self-hostable, official MCP), Linkup, Parallel, Serper/SerpAPI (cheap raw Google SERP, ~$0.30–1/1k).

A useful framing from serp.fast: classify by primitive — **Full** APIs (Perplexity Sonar, Parallel) return synthesized answers; **Fast** APIs (Tavily, Exa Fast/Instant, You.com) return LLM-ready snippets; **Index** APIs (Exa, Brave) give raw semantic/keyword index access you rank yourself. Since Claude is your synthesizer, you want the Fast/Index tiers, not Full.

### 4. Self-hosted search: SearXNG

SearXNG is a mature, actively-maintained open-source metasearch engine (15k+ GitHub stars; stable v1.5.x line in 2026) that aggregates 70+ engines (Google, Bing, DuckDuckGo, Brave, Wikipedia, Startpage…) with no tracking.  **Setup is genuinely easy**: Docker/Docker Compose is the standard path; it runs comfortably on a personal Mac or a $5–6/month VPS using ~200MB RAM.  For programmatic use you enable the JSON format in `settings.yml` (`search.formats`), then query `GET /search?q=<query>&format=json`, which returns structured results with `title`, `url`, `content`, and `engine` fields per result  — exactly what an MCP server needs. LangChain, LiteLLM, n8n, and Flowise all ship built-in SearXNG integrations.  **The one real caveat**: SearXNG scrapes public engines, so under heavy load Google/Bing may rate-limit or CAPTCHA your instance’s IP; for personal/internal research volume this is rarely an issue  (one user reports 4 months trouble-free). This is the realistic free replacement for the *discovery* half of Exa.

### 5. Self-hosted content extraction

Independent benchmarks converge on **Trafilatura (Python, by Adrien Barbaresi) as the accuracy leader** among open-source extractors. On the Scrapinghub/Zyte article-extraction-benchmark, trafilatura scores F1 0.945 (±0.009; precision 0.925, recall 0.966), ahead of go_readability (0.943) and readability_js (0.887). Bevendorff et al.‘s SIGIR 2023 study (“An Empirical Comparison of Web Content Extraction Algorithms,” 8 datasets / 14 extractors) found Trafilatura had the best overall mean F1 (0.883) while Readability.js had the highest median (0.970); the Sandia SAND2024-10208 evaluation likewise put Trafilatura at the top on mean F1/precision. It uses a heuristic pipeline with fallback algorithms — no ML, no GPU — at roughly **14–22ms per page**, and outputs plain text, Markdown, JSON, or cleaned HTML. Production use at HuggingFace, IBM, Microsoft Research.  A Rust port (`rs-trafilatura`, by Murrough Foley) scores even higher on the ScrapingHub set — **F1 0.966 (precision 0.942, recall 0.991)**, ahead of go-trafilatura (0.960) and Python trafilatura (0.958), with the archived benchmark’s final run at 0.970 ±0.0047 — at ~44ms/page; on the broad WCXB multi-type benchmark (2,008 pages, 7 page types) rs-trafilatura scores F1 0.859 dev / 0.893 held-out, and with a MinerU-HTML fallback for low-confidence pages reaches the top WCXB held-out F1 (0.910). **Recommendation: Trafilatura as the default extractor**, with Jina Reader (cloud) or a Playwright/Crawl4AI render as fallback for JS-heavy SPAs (Trafilatura, like Claude’s own fetch, only sees the initial HTML). Alternatives: Mozilla Readability.js / readabilipy (cleaned HTML only), newspaper4k (news + built-in NLP/multilingual), Unstructured.io (heavier, multi-format document parsing), neural models like Jina ReaderLM-v2 (1.54B params, better structural fidelity but needs GPU and is orders of magnitude slower). 

### 6. Architecture for a custom “semantic web fetch” MCP server

The pattern you describe — fetch → extract clean text → chunk → embed chunks locally → embed query → return top-K relevant chunks — is a **local, on-the-fly RAG step over each fetched page**, and it is exactly what Exa’s highlights do internally. Existing open-source implementations of this pattern, per research:

- **`coleam00/mcp-crawl4ai-rag`** (~2.2k stars, MIT) — the canonical version: crawls URL/sitemap → chunks → embeds → stores in **Supabase (PostgreSQL + pgvector)** → `perform_rag_query` re-queries without re-fetch. Supports contextual embeddings, hybrid vector+keyword search, and a local cross-encoder reranker (`ms-marco-MiniLM-L-6-v2`). **But it embeds via OpenAI by default; local Ollama is roadmap, not shipped.**
- **`ToKiDoO/crawl4ai-rag-mcp`** — Docker stack bundling Crawl4AI + SearXNG + Supabase/pgvector in one compose file (very close to your target topology).
- **`shinpr/mcp-local-rag`** — local embeddings (Transformers.js `all-MiniLM-L6-v2`), semantic chunking, hybrid semantic+keyword, quality-gap filtering instead of fixed top-K,  persists to local vector DB + FTS, fully offline. Ingests HTML/files passed to it (the AI fetches; the server embeds).
- **`nkapila6/mcp-local-rag`** — “primitive” web-search RAG MCP: DuckDuckGo → fetch top results → embed with Google MediaPipe → rank → return top-K markdown.  No API keys, but **in-memory** (no persistence).
- **`dondai1234/master-fetch` (“Hound”)** — MCP web fetcher with Trafilatura extraction, Cloudflare bypass, 10-backend keyless parallel search with neural reranking, and a `find_similar` (Exa-style) tool.  Persists an **on-disk SQLite fetch cache** with TTL, and does query-focused extraction via **BM25 (keyword), not embeddings**. Notably tuned for low tool-overhead (~2.7K tokens for 6 tools vs Firecrawl/Jina’s much larger footprints). 
- **`n24q02m/wet-mcp`** — zero-config MCP with embedded local SearXNG + local Qwen3 embedding/reranking, 5-strategy scraping escalation. 

**For your build**, the MLX embedding layer is well-supported on the M5 Max: options include `mlx-serve` (OpenAI-compatible, hot-swaps LLM/embedding models, auto-unloads on idle to respect unified-memory limits),  `jakedahn/qwen3-embeddings-mlx` (Qwen3-Embedding 0.6B/4B/8B, ~44K tokens/sec on the small model),  and `cubist38/mlx-openai-server`. MLX reportedly outperforms llama.cpp on embedding (prefill-bound) workloads by ~50% at batch sizes >16.  Best local embedding models on Apple Silicon per a June 2026 comparison: `nomic-embed-text-v2` (137M, 8192 ctx), `bge-m3` (568M, multilingual dense+sparse+colbert), and `Qwen3-Embedding-8B` (top of MTEB, 32K ctx).  Add a **local cross-encoder reranker** — `BAAI/bge-reranker-v2-m3` (568M) is the standard open pick, running the “retrieve top-20 via embeddings, rerank to top-5” pattern  that typically adds +5 to +15 NDCG@10  — to squeeze out the last relevance gains, mirroring Exa’s approach. Since Claude’s own web_fetch security model only fetches URLs already in context, a custom MCP tool that can fetch arbitrary URLs (from a SearXNG search result) is also a functional upgrade, not just a token optimization.

### 7. Caching fetched content locally for reuse

Persisting each fetched page’s chunks + embeddings into Mnemosyne’s pgvector store to build a **growing, re-queryable personal web index** is sound and well-precedented. pgvector handles millions of vectors on a single Postgres instance with HNSW indexing,  supports hybrid (vector + `tsvector` BM25) queries with RRF natively in SQL (exactly Mnemosyne’s existing pattern), and `halfvec` half-precision storage halves vector storage at minor accuracy cost. Prior art / reference patterns: `coleam00/mcp-crawl4ai-rag` and `ToKiDoO/crawl4ai-rag-mcp` (pgvector web caches); `Geeksfino/kb-mcp-server` (txtai with a `postgres-pgvector.yml` backend); pgvector-backed agent-memory MCPs (`petabridge/memorizer` with local Ollama `nomic-embed-text`, `sdimitrov/mcp-memory` with local BERT); the “personal web index” concept in **Remio** (indexes files, webpages, notes for agent RAG); the academic **WebCoach** (arXiv 2511.12997) “External Memory Store” of per-episode embedding+summary+metadata in FAISS/HNSW for cross-session reuse; and **memweave**‘s “compute-once” `embedding_cache` (hash→vector) table pattern. Design notes: key the cache by URL + content-hash + extractor + chunking params (so a re-fetch that returns identical content is a no-op), store a TTL/fetched-at for freshness, and — per the VoiceAgentRAG paper — index cached chunks by their *own* document embeddings, not by the original query embedding, or you’ll get spurious cache hits. 

### 8. Comparison and recommendation

**Token savings are real and large.** Independent and vendor measurements cluster as follows: a typical web page is ~38,000 tokens of raw HTML wrapping ~2,800 tokens of actual content  — Firecrawl/Trafilatura-style markdown extraction is a ~94% reduction (~$0.11/page saved at Sonnet 4.6 $3/M input; ~$1.14/session of noise on a 10-page research session).  HTML→Markdown alone is commonly ~30–70% (one independent 10-page test found raw HTML costs ~7.4× median more tokens). Adding *query-relevant chunk selection* on top (the Exa-highlights step) pushes savings to the ~94% / 16×-fewer-tokens range Exa reports, while *improving* answer accuracy because it fights “context rot”/“lost in the middle.” Note Claude’s native web_fetch now has a `max_content_tokens` cap and (on recent models) a “dynamic filtering” mode where Claude writes code to trim fetched content before it hits context (~24% fewer input tokens, ~11% accuracy gain per Anthropic)  — so the baseline you’re improving on is already moving.

|Axis                    |Exa API (direct/MCP)                         |Jina Reader (cloud)                   |SearXNG + Trafilatura + local embed (build)             |
|------------------------|---------------------------------------------|--------------------------------------|--------------------------------------------------------|
|Build cost/complexity   |Lowest (native connector)                    |Low                                   |Highest (custom MCP, but reuses Mnemosyne)              |
|Per-query cost          |$7/1k search (+$10/mo free)                  |~$0.02/1M tokens                      |**$0** (electricity)                                    |
|Result quality          |Best neural recall; highlights ~16× token cut|Clean markdown, no relevance filtering|Extraction = SOTA; recall limited to SearXNG’s upstreams|
|Privacy / data residency|Queries + URLs sent to Exa                   |URLs sent to Jina/Elastic             |**Fully local — nothing leaves the M5 Max**             |

## Recommendations

**Stage 0 — Immediate (this week): install Exa’s MCP server and measure.** Add the free hosted `https://mcp.exa.ai/mcp` connector to Claude and use `web_search_exa` + highlights for a week. It’s zero-build, and it gives you a concrete quality/token baseline to beat. If Exa’s highlights alone solve your token problem and the ~$7/1k (after free credits) is acceptable for your volume, you may not need to build anything — *decision threshold: if your monthly search volume × $7/1k stays under ~$10–20 and none of the queries are sensitive, just use Exa.*

**Stage 1 — Build the local extraction MCP (highest ROI, low risk).** Stand up a custom MCP server that exposes a `semantic_fetch(url, query)` tool: fetch → **Trafilatura** extract → chunk → embed chunks and the query via your **MLX embedding server** (start with `bge-m3` or `nomic-embed-text-v2`; both fit comfortably in 48GB) → return top-K chunks, optionally reranked by **`bge-reranker-v2-m3`**. This captures ~90%+ of the token savings, keeps fetched content fully local, and reuses Mnemosyne’s embedding infra directly. Fork `shinpr/mcp-local-rag` or `dondai1234/master-fetch` as a starting skeleton rather than greenfielding.

**Stage 2 — Add self-hosted discovery.** Run **SearXNG in Docker** on the Mac (or a cheap VPS) and add a `web_search(query)` tool to the same MCP server that hits `/search?...&format=json`, then pipes chosen URLs into your Stage 1 `semantic_fetch`. This removes the last dependency on a paid search API. *Threshold to keep a paid API instead: if SearXNG’s recall/freshness proves inadequate for your topics (test on 30–50 real queries), keep Exa or Brave as the discovery backend behind the same tool interface — the MCP boundary makes this swappable.*

**Stage 3 — Persist to pgvector (the personal web cache).** Extend `semantic_fetch` to write each page’s chunks+embeddings into a new Mnemosyne pgvector table (keyed by URL+content-hash+chunk params, with fetched-at TTL), and check the cache before re-fetching. Reuse Mnemosyne’s existing hybrid RRF query path so past web research becomes searchable alongside your code/memory. Index chunks by their own embeddings, not the query’s.

**What would change these recommendations:** If you find you need JS-rendered pages frequently, add Crawl4AI (Playwright, Apache-2.0, self-hostable)  or Jina Reader as a fallback renderer in Stage 1. If per-query neural *recall* (finding the right URLs for fuzzy/conceptual queries) turns out to matter more than extraction quality, weight spend toward keeping Exa as the discovery layer, since that index is the one component you cannot cheaply reproduce locally.

## Caveats

- **Freshness vs recall trade-off**: embedding/neural indexes (Exa) and semantic caches are weaker on breaking news; keyword engines (SearXNG’s Google/Bing/Brave upstreams) win there. Your local stack actually helps here since SearXNG hits live engines.
- **SearXNG depends on scraping public engines** and can be rate-limited/CAPTCHA’d under load; fine for personal research volume, risky for high-throughput automation.
- **Vendor token-savings figures (Firecrawl, AlterLab, Web2MD, Exa) are partly marketing.** The directionally-reliable independent anchors: ~38k→2.8k tokens/page raw-HTML→markdown, and Exa’s own eval of highlights (~94% / 16×). Treat the higher “up to 95%” claims as best-case.
- **Local embedding ≠ zero quality gap**: a small local model (all-MiniLM, nomic) will retrieve slightly worse than a top cloud embedding or Exa’s tuned highlights model; the local reranker is what closes most of that gap. Benchmark on your own query set.
- **Privacy nuance**: general public-web search is low-sensitivity even if sent to Exa/Brave; the higher-value privacy win of the local stack is that *fetched page content and your query phrasing* — which can reveal what you’re working on — never leave your machine. Given Adobe-adjacent work, keeping the fetch+extract+cache local is the prudent default, while a paid discovery API for non-sensitive lookups is an acceptable hybrid.
- **Moving baseline**: Claude’s native web_fetch/web_search added `max_content_tokens` and code-based dynamic filtering in 2026, narrowing the gap versus a custom solution for casual use — your build’s durable advantages are *privacy, $0 marginal cost, the reusable pgvector cache, and arbitrary-URL fetching*, more than raw token savings alone.
- **No turnkey product matches your exact spec** (web fetch + local embeddings + pgvector + MCP re-query). You’ll be integrating existing pieces, not installing one tool — which is why the staged build above starts from an existing skeleton and adds your Mnemosyne-specific layers incrementally.
